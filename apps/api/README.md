# api

The NestJS API (`deploy-api-skeleton`), with its PostgreSQL connection and migration history (`add-persistence-skeleton`), and the composition of every context, starting with `identity` (`add-identity-authentication`).

- **Database.** The API connects to the database `DATABASE_URL` names and refuses to start without it. The connection is opened on the first query, so `/health` answers whether or not the database is reachable. The pool and the Drizzle database are provided by `src/database/database.module.ts`.
- **Migrations.** One drizzle-kit history (ADR-0011): `drizzle.config.ts` reads every context's schema through `src/database/schema.ts` and writes to `migrations/`, which ships in the image beside `dist/`. Generate a migration after changing a schema with `pnpm nx run api:db-generate` (no database needed; it builds the libraries the schemas come from first), and review the SQL it writes. A context's tables live in its own PostgreSQL schema, never `public`, and `src/database/schema.ts` re-exports the `pgSchema` object with them so drizzle-kit creates the schema. Apply the history with `pnpm nx build api` then `DATABASE_URL=postgres://… node apps/api/dist/migrate.js`; deliveries run the same command as the Compose service `migrate` before the API starts. It exits `1` on any failure, printing the error with the URL and its password redacted.
- **Configuration.** `src/config/` validates `DATABASE_URL` (required), `PORT` (default `3000`, `1`–`65535`), `APP_VERSION` (default `unknown`), `GOOGLE_CLIENT_IDS` and `SIGNUP_ALLOWED_EMAILS` (both comma-separated, unset meaning none) with Zod when the API is created, and provides them under `APP_CONFIG`. An invalid environment stops the API before it listens, naming each invalid variable and never its value. Nothing else in `src/` reads `process.env` (lint), except `migrate.ts`.
- **Logs.** One JSON object per line, through Nest's `ConsoleLogger` (`src/logging/`). Properties named as secrets (`SECRET_KEYS`: `password`, `token`, `apiKey`, `databaseUrl` and the rest, in any letter case and at any depth) are written as `[REDACTED]`. Redaction does not reach message strings, error messages or stacks, so **a secret goes only into a log entry's structured params, never into its message**: `logger.log('Connected.', { databaseUrl })`, never ``logger.log(`Connected to ${url}.`)``.
- **Errors.** Every error response is an RFC 9457 problem document (`application/problem+json`: `type` `about:blank`, `title`, `status`, and `detail`, `code` or `errors` where they apply), rendered by `src/http/problem.filter.ts`. A controller answers a handler's `Result` with `toResponse(result)` from `@basis/shared-infrastructure`: a `DomainError`'s kind sets the status (`not-found` 404, `conflict` 409, `rule-violated` 422, `forbidden` 403, `unauthenticated` 401 with `WWW-Authenticate: Bearer`). A route parameter whose decorator names a schema (`@Body({ schema })`, from a context's `contracts`) is validated, and refused with `400` and its issues. A defect, or an HTTP exception of `500` or above, is answered without its message and logged.
- **Sign-in and sessions** (`identity`). Every route requires `Authorization: Bearer <session token>` unless it is marked `@Public()` (from `@basis/shared-infrastructure`); without one it answers `401` with `WWW-Authenticate: Bearer`. A controller reads its caller with `@CurrentUser()`, `{ userId }`. `POST /auth/google` (public) takes `{ "idToken" }`, a Google ID token whose audience is one of `GOOGLE_CLIENT_IDS`, and answers `{ token, expiresAt }`: a session valid for 30 days, stored only as its SHA-256 digest. `POST /auth/sign-out` revokes the presented session; `GET /me` answers `{ id, email, displayName }`. With `GOOGLE_CLIENT_IDS` unset, every ID token is refused and a warning is logged at startup.
- **Who may create an account.** Only a Google account whose verified email is in `SIGNUP_ALLOWED_EMAILS`; unset admits nobody new. Each deployment sets its own list (the Environment secret `BASIS_API_SIGNUP_ALLOWED_EMAILS`, and the variable `BASIS_API_GOOGLE_CLIENT_IDS` for the client IDs), so a fork names its own people and the repository names nobody. The list is checked only when an account is created: removing an email does not lock out its account. A malformed entry in either variable stops the API at startup, which fails a delivery.
- **A test ID token.** In Google Cloud, create an OAuth client of type Web application with `https://developers.google.com/oauthplayground` as an authorised redirect URI. In the [OAuth Playground](https://developers.google.com/oauthplayground), under the settings, use your own OAuth credentials with that client's ID and secret, authorise the scopes `openid` and `email` (and `profile` for a name), exchange the code, and copy `id_token`. It is valid for an hour: `curl -X POST -H 'content-type: application/json' -d '{"idToken":"<id_token>"}' https://<host>/auth/google`.
- **Body limits.** A JSON body over 100 kB is refused `413`, except at `POST /health-connect/deliveries`, which accepts 10 MB (`src/http/body-parsers.ts`, applied by `main.ts` before the application initialises).
- **The Health Connect intake** (`metrics`, temporary: roadmap Phase 0, retired by Phase 1's ingestion). `POST /health-connect/deliveries` stores an [HC Webhook](https://github.com/mcnaveen/health-connect-webhook) delivery unchanged for the caller and answers `204`; `GET /health-connect/deliveries/summary` answers what the caller's deliveries hold: data types, the apps, devices and recording methods behind them, sleep stages, exercise types, and how long records took to reach Health Connect and then the API. A delivery's contents are never logged. To send a phone's data:
  1. Sign in on the host you send to and keep the session token (see _A test ID token_; each host has its own sessions).
  2. In HC Webhook, grant Health Connect read access to only the types the habits need: steps, distance, active and total calories, heart rate, resting heart rate, heart rate variability, sleep, exercise.
  3. Add a webhook with the URL `https://<host>/health-connect/deliveries`, delivery format JSON, and the custom header `Authorization` with the value `Bearer <session token>`.
  4. Set heart rate (and the other series) to raw samples (Full resolution), so zones can be judged; aggregates are counted under `shapes`.
  5. Run a manual sync; the webhook log should show `204`. Then read the summary: `curl -H "authorization: Bearer <session token>" https://<host>/health-connect/deliveries/summary`.

  The bridge's log showing `401` means the session expired (30 days) or was revoked: sign in again and replace the header. `413` means a delivery exceeded 10 MB, likeliest on a first sync: enable fewer types until it passes, then the rest. A summary whose `deliveries.lastReceivedAt` stops advancing means deliveries are failing.

- **Tests.** Unit specs beside their files (`pnpm nx test api`); integration specs in `tests/integration/` against a throwaway PostgreSQL per run (`pnpm nx run api:integration`, needs Docker); end-to-end in `apps/api-e2e`.
