# ADR-0005: Nx monorepo on top of pnpm workspaces

**Status:** accepted · **Date:** 2026-10-17

## Context

Three apps (mobile, web, api) share types, schemas, habit rules, and the API client. The product is designed to grow: the codebase is split into bounded contexts (ADR-0010) whose boundaries must be **enforced**, not just agreed upon. The team has Nx experience.

## Decision

**Nx** orchestrates the monorepo on top of **pnpm workspaces**:

- Nx handles the project graph, task running, caching, `nx affected` in CI, and **module boundary enforcement** (`@nx/enforce-module-boundaries`).
- `apps/api` — `@nx/nest`; `apps/web` — `@nx/vite`.
- `apps/mobile` — first validate `@nx/expo` against the current Expo SDK. If the plugin lags or conflicts with Metro, the app keeps standard Expo scripts (`expo start`, `eas build`) but remains a project in the Nx graph (caching and boundaries still apply).
- Shared code lives in `libs/<context>/<layer>` with `scope:*` and `type:*` tags (structure — `docs/architecture/context-map.md`).

### Boundary rules

| Tag | May depend on |
|---|---|
| `type:util` | `type:util` only |
| `type:contracts` | `type:contracts`, `type:util` |
| `type:domain` | `type:domain` of the same scope, `type:util` |
| `type:application` | `type:domain` and `type:contracts` of the same scope; `type:contracts` of other scopes; `type:util` |
| `type:infrastructure` | `type:application`, `type:domain`, `type:contracts` of the same scope; `type:contracts` of other scopes; `type:util` |
| `type:feature` (simple contexts) | `type:contracts` of any scope, `type:util`, `type:data-access` |
| `type:data-access` | `type:contracts`, `type:util` |
| `scope:<context>` | its own scope, `scope:shared`, and **only `contracts`** of other contexts |
| apps | any library |

## Alternatives considered

- **pnpm workspaces without an orchestrator** — simplest, but no caching, `affected`, or boundary enforcement.
- **Turborepo** — caching and task running, but no built-in module boundary enforcement.
- **Separate repositories** — type drift, harder evolution.

## Consequences

+ Architectural boundaries are checked by the linter, including for code generated by Claude Code.
+ Faster CI as the number of projects grows (`nx affected`, caching).
+ Project graph and generators for typical libraries and modules.
− More configuration than plain pnpm workspaces.
− Regular upgrades via `nx migrate`.
− Risk of `@nx/expo` drifting from the Expo SDK — mitigated by the fallback to standard Expo scripts.
