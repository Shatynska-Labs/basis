## Context

See proposal.md, Why. `apps/api` is a NestJS 12 application with a validated configuration (`APP_CONFIG`, `apps/api/src/config/`), JSON logs, a global `ProblemFilter` and a global Standard Schema validation pipe (`api-http-errors`). The Drizzle database is provided under `DATABASE` from `@basis/shared-infrastructure`, which is built to `dist/` and imported at runtime. `@basis/shared-core` (`Result`) and `@basis/shared-domain` (`DomainError`, kinds `not-found`, `conflict`, `rule-violated`, `forbidden`) are unbuilt and imported by nothing shipped. Nx's `enforceBuildableLibDependency` refuses any import of an unbuilt library from a built one, specs included, and `libs/shared/testing` is unbuilt. drizzle-kit owns one migration history in `apps/api`, collecting schemas through `apps/api/src/database/schema.ts`; it holds only a baseline. No context library exists, and `@nestjs/cqrs` is not installed. The context map places `identity` as a generic context with no `domain` layer, holding `User` and `Profile`. Each host's database holds only data whose loss is tolerable (`choose-durable-data-storage`). Neither a web nor a mobile client exists.

## Goals / Non-Goals

**Goals:**

- A caller of the API is identified by a session obtained by signing in with Google, and every route requires one unless it is declared public.
- Only people the deployment names can create an account, with nothing personal written in the public repository.
- The shape every later context follows: `application`, `infrastructure`, `contracts`, CQRS buses, Drizzle tables in the context's own schema, and the caller taken from the shared infrastructure.

**Non-Goals:**

- The profile (time zone, heart-rate zone parameters): the next change, `add-identity-profile`.
- Sign-in from a web or mobile client, and how a web client holds its session (bearer header or cookie): decided when `apps/web` exists.
- Invitations that let a user admit another without a redeploy: `invite-users-to-sign-up` in `docs/backlog.md`.
- Account deletion and data export (PRD privacy requirements), rate limiting, refresh tokens, listing or revoking other sessions.
- Revoking an existing account when its email leaves the allowlist.
- A `TransactionManager` (ADR-0011 rule 2): no write in this change spans two repositories in a way that needs one (decision 6).

## Decisions

1. **Google ID tokens only, verified by the API with `jose`** (operator's decision: Google only, hand-rolled). A client obtains an ID token from Google (Credential Manager on Android, Google Identity Services on the web, the OAuth Playground for an operator) and posts it. The verifier checks the RS256 signature against Google's JSON Web Key Set (`https://www.googleapis.com/oauth2/v3/certs`, fetched and cached by `jose`'s `createRemoteJWKSet`), `iss` is `accounts.google.com` or `https://accounts.google.com`, `aud` is one of the configured client IDs, `exp` has not passed, allowing 30 seconds of clock skew (`clockTolerance: 30`), and `email_verified` is `true`. With no configured client ID it refuses every token before any verification. A token failing a check is `InvalidIdToken`; a failure to obtain the key set (network error, timeout, a non-`200` answer from Google) is not the client's fault, so the verifier throws and the API answers it as a defect, `500`, logged. It yields `{ subject, email, displayName }` from `sub`, `email` and `name` (absent `name` is `null`). Alternatives: `google-auth-library` (official, but six dependencies and an HTTP client for one verification); Better Auth (operator declined: it owns its routes, schema and error format). `jose` has no dependencies and verifies against a local key set in tests, so no test reaches Google.

2. **Sessions are opaque random tokens stored as hashes.** On sign-in the API generates 32 random bytes (`node:crypto` `randomBytes`), encodes them base64url (43 characters) as the token, and stores only its SHA-256 hex digest with the user's identifier, `created_at`, `expires_at` (creation + 30 days) and a nullable `revoked_at`. The token is returned once and never logged or stored. A request authenticates with `Authorization: Bearer <token>`; the session is valid when its hash is found, `expires_at` is later than now and `revoked_at` is null. There is no sliding renewal: a client signs in again, which on Android is silent. Alternatives: signed JWTs (no lookup per request, but no revocation without a deny list); Redis-backed sessions (Redis is not deployed, and `choose-durable-data-storage` is undecided).

3. **Sign-up is restricted by a per-deployment allowlist** (operator's decision). `SIGNUP_ALLOWED_EMAILS` is a comma-separated list in the configuration; entries are trimmed and lowercased, and an empty entry (`a@x.org,,b@x.org`) is skipped. It is checked only when a Google account with no user signs in: its verified email, lowercased, must be on the list, or sign-in fails with kind `forbidden`, code `identity.sign-up-not-allowed`. A known Google account signs in whether or not its email is listed. Unset or empty lets nobody create an account. Each deployment sets its own list, so a fork names its own people and the repository names nobody.

4. **The user is matched by Google subject, not by email.** `users` holds `id` (UUID, generated by the database), `google_subject` (unique), `email`, `display_name` (nullable) and `created_at`. On every sign-in of a known subject the stored `email` and `display_name` are updated from the token, since Google is their source. `email` is not unique: Google may reassign an address, and the subject is the stable identity.

5. **Library layout follows ADR-0012 §1** without `domain`:
   - `libs/identity/contracts` (`@basis/identity-contracts`, `scope:identity`, `type:contracts`): the Zod schemas `SignInWithGoogleRequest` (`{ idToken: string }`, non-empty), `SessionResponse` (`{ token, expiresAt }`, `expiresAt` an ISO 8601 string with offset) and `CurrentUserResponse` (`{ id, email, displayName }`).
   - `libs/identity/application` (`@basis/identity-application`, `type:application`): commands `SignInWithGoogle` and `SignOut`, queries `AuthenticateSession` and `GetCurrentUser`, each in its own folder with its handler; ports `GoogleIdTokenVerifier`, `Clock`, and read and write repositories kept apart (ADR-0012 §1, §2): write ports `UserRepository` (find by Google subject; save by Google subject, returning the user's identifier) and `SessionRepository` (add, revoke), read ports `UserReader` (the current user by identifier) and `SessionReader` (the user of a valid session by token digest); failures `InvalidIdToken` (kind `unauthenticated`, code `identity.invalid-id-token`), `SignUpNotAllowed` (`forbidden`, `identity.sign-up-not-allowed`), `InvalidSession` (`unauthenticated`, `identity.invalid-session`), all extending `DomainError` and returned in a `Result`. Token generation and hashing use `node:crypto` directly, which the external-import constraints allow.
   - `libs/identity/infrastructure` (`@basis/identity-infrastructure`, `type:infrastructure`): `driven/` holds the Drizzle tables (`pgSchema('identity')`), the repository and reader adapters, `JoseGoogleIdTokenVerifier` and the system clock; `driving/` holds `AuthController`, `MeController` and `SessionGuard`. The composition root, `src/identity.module.ts`, sits outside both folders: it binds the driven adapters to the application's ports and registers the driving adapters, so neither folder imports the other.

   ADR-0012 §1's rule that a driving adapter reaches a driven one only through `application` is enforced from this first context: in the root `eslint.config.mjs`, files under `libs/*/infrastructure/src/driving/**` may not import from `driven/` (any relative path containing `/driven/`). Flat config replaces a rule configured twice for one file rather than merging it, so the rule takes two blocks: one for the driving folder's non-spec files, with the shared-testing block's `ignores`, repeating the shared-testing patterns beside the `/driven/` one; and one for its specs, with only the `/driven/` pattern, so a driving spec may still import `@basis/shared-testing`.

   All three are built like `shared-infrastructure` (`share-the-database-connection` decision 5) and are `dependencies` of `apps/api`. `IdentityModule.forRootAsync({ inject, useFactory })` takes `{ googleClientIds, signupAllowedEmails }`, so `AppModule` passes them from `APP_CONFIG` and `identity` never sees the app's configuration type.

6. **No transaction.** Saving a user is one statement, `INSERT … ON CONFLICT (google_subject) DO UPDATE SET email, display_name … RETURNING id`, so two concurrent first sign-ins of one subject yield one user and two sessions rather than a unique violation. The handler checks the allowlist before saving, from whether a user with that subject exists (`UserRepository`'s lookup by subject). The session is inserted after; if that fails the user remains, without a session, and the next sign-in finds it by subject. Sign-out updates one row. ADR-0011's `TransactionManager` is left to the first change whose writes must be atomic.

7. **The session requirement is global and public routes are declared.** `SessionGuard` is registered by `IdentityModule` as `APP_GUARD`. A handler or controller marked `@Public()` passes without a session. Otherwise the guard reads `Authorization`; a missing header, a scheme other than `Bearer` (case-insensitive), an empty token, or an `InvalidSession` from `AuthenticateSession` is answered `401` with a `ProblemException` (`detail` `"Authentication is required."`, `code` `identity.invalid-session`, header `WWW-Authenticate: Bearer`). On success it sets the request's authenticated user to `{ userId }`. `AuthenticatedUser` stays `{ userId }`, since other contexts need nothing more; `POST /auth/sign-out` reads the bearer token from `Authorization` itself, through the same parsing function the guard uses, and sends it in `SignOut`, whose handler revokes the session with that token's digest and that user. `Public`, `CurrentUser` (a parameter decorator returning `AuthenticatedUser`) and `AuthenticatedUser` live in `libs/shared/infrastructure/src/driving/authentication.ts`, so another context's controllers read the caller without depending on `identity`'s infrastructure, which `scope:<context>` forbids. `CurrentUser` on a public route without a session throws, a defect. `HealthController` is marked `@Public()`. Nest's handler for an unknown route runs no guard, so an unknown route stays a `404` (`api-http-errors`); a spec checks it. `ProblemException` gains an optional `headers` member that `ProblemFilter` sets on the response.

8. **Routes.**
   - `POST /auth/google` (public), body `SignInWithGoogleRequest`: `200` with `SessionResponse`; `401` for `InvalidIdToken`; `403` for `SignUpNotAllowed`; `400` for a body failing its schema.
   - `POST /auth/sign-out`: revokes the presented session; `204`.
   - `GET /me`: `200` with `CurrentUserResponse`.

   Controllers send commands and queries on the buses and map results with `toResponse`.

9. **Kind `unauthenticated`, answered `401`.** `DomainErrorKind` gains `unauthenticated`, and `toResponse`'s status map gains `401`, so a handler's authentication failure maps like any other. Because RFC 9110 §15.5.2 requires a `401` to carry `WWW-Authenticate`, `toResponse` sets `WWW-Authenticate: Bearer` on the `ProblemException` for that kind, the API's only scheme. `http-errors.spec.ts` already fails `apps/api`'s typecheck if the kinds and the map diverge (`add-api-cross-cutting-basics` decision 7). In the `shared-domain` delta, the scenario "Only the four kinds type-check" keeps its recorded name: `openspec validate --strict` 1.14.2 refuses a `MODIFIED` block that omits a scenario of the current requirement by name ("archive refuses to drop them"), checked while drafting. What it asserts, that an unknown kind does not type-check, still holds.

10. **Configuration.**
    - `GOOGLE_CLIENT_IDS`: unset or empty yields `googleClientIds` `[]`, and then every ID token is refused as `InvalidIdToken`, since no audience can match; the API logs one `warn` entry at startup, `Sign-in with Google is disabled: GOOGLE_CLIENT_IDS names no client.` Otherwise a comma-separated list, entries trimmed, empty entries skipped, each matching `^[A-Za-z0-9.-]+\.apps\.googleusercontent\.com$`. Optional at the API, so local runs and existing specs need no Google client; required at delivery (decision 11).
    - `SIGNUP_ALLOWED_EMAILS`: unset or empty yields `[]`. Otherwise entries trimmed and lowercased, empty entries skipped, each matching `^[^\s@,]+@[^\s@,]+\.[^\s@,]+$`.

    A refusal names the variable with a fixed description and no value, as `api-configuration` already requires.

11. **Delivery.** `deploy.yml` and `promote.yml` pass `${{ vars.BASIS_API_GOOGLE_CLIENT_IDS }}` and `${{ secrets.BASIS_API_SIGNUP_ALLOWED_EMAILS }}` to the deliver action as `google-client-ids` (required: the first step refuses without it) and `signup-allowed-emails` (optional). Both reach `render-env.ts` through `env:` and are rendered with `renderLine` as `GOOGLE_CLIENT_IDS` and `SIGNUP_ALLOWED_EMAILS`. Rendering refuses client IDs in which no entry remains once split on commas and trimmed (`""`, `" "`, `","`), naming `GOOGLE_CLIENT_IDS`, so a delivered host never has sign-in disabled; it does not otherwise validate them, and the API's configuration refuses a malformed entry at startup, failing the delivery's `up --wait`. The same holds for a malformed allowlist: the API refuses to start and the delivery fails naming the variable in the container's log. The allowlist is personal data, so it is a secret, and neither it nor any `.env` line is printed. Client IDs are public, so they are a variable. A promotion of a commit from before this change renders the two lines into a `.env` its API ignores.

12. **Builds and the buildable-library rule.** `identity`'s libraries import `Result` and `DomainError` at runtime, so `shared-core` and `shared-domain` become buildable as `shared-infrastructure` did (`share-the-database-connection` decision 5). In the root `eslint.config.mjs`, the boundary rule for specs and test and lint configuration (`boundaries(false)`) sets `enforceBuildableLibDependency: false`: specs are excluded from every library's build output, so the rule's reason, built code importing unbuilt sources, does not arise, and a built library's specs may then import `@basis/shared-testing`. Production files keep the rule. The `add-api-cross-cutting-basics` decision 7 structural shapes in `toResponse` stay; replacing them is not this change's work.

13. **External imports.** `jose` joins `frameworkAndSdkPackages` (it fetches over HTTP), so only `infrastructure` may import it. `@nestjs/cqrs` is already covered by `@nestjs/*` and allowed in `application` (ADR-0012 §7). Versions: the newest the workspace's minimum release age admits, exact.

14. **Migration.** drizzle-kit generates `0001` from `identity`'s tables, re-exported by `apps/api/src/database/schema.ts`: schema `identity`, tables `users` and `sessions` (`sessions.user_id` references `users.id` on delete cascade; `token_hash` unique). Forward-only and additive, so the previous release runs against it. `api-persistence`'s baseline scenario, which said a migrated database holds no table outside the migration record, is amended to hold no table in `public` and every other table in its context's schema (found while deriving tests).

15. **Verification.** Unit specs cover the handlers with in-memory fakes and a fixed clock, the verifier against a locally generated RSA key set (`jose`'s `createLocalJWKSet`, injected in place of the remote set), the guard and controllers through an application built from `IdentityModule` with fakes, and the configuration and rendering rules. Integration specs in `apps/api/tests/integration/` cover the repositories against a migrated database, since `apps/api` owns the migration history. The e2e suite covers `401` for `GET /me` without a session and `/health` staying public.

## Risks / Trade-offs

- [A leaked session token grants access for up to 30 days] → sign-out revokes it; tokens are never logged, and only hashes are stored. Revoking all of a user's sessions is out of scope.
- [The allowlist is checked only at account creation] → removing an email does not lock out its account; stated in the README. Accounts are few and known to the operator.
- [Google's key set is fetched at runtime] → `jose` caches it and refetches on an unknown key ID; if Google is unreachable, sign-in answers `500` and is logged (decision 1), while existing sessions keep working.
- [The database is unreachable after startup] → every route needing a session answers `500`, a defect, while `/health` stays `200`, as `api-persistence` intends.
- [`Public` and `CurrentUser` extend the shared infrastructure while `share-the-database-connection`, which specifies that library as the capability `shared-infrastructure`, is merged but not yet archived] → this change states its addition as an `ADDED` requirement of `shared-infrastructure`, which archives whichever of the two goes first; it does not depend on that change, whose code is already on the trunk.
- [Data on each host is loss-tolerable] → losing `users` and `sessions` means signing in again; acceptable until `choose-durable-data-storage`.
- [Bearer tokens in a future web client invite storage in `localStorage`] → deferred to the change that adds `apps/web`.
- [The global guard makes every new route private by default] → intended; a public route is a visible `@Public()`.

## Migration Plan

Before merging, the operator creates a Google Cloud OAuth client (type Web application, with `https://developers.google.com/oauthplayground` as an authorised redirect URI for confirming on staging), and sets in both Environments the variable `BASIS_API_GOOGLE_CLIENT_IDS` and the secret `BASIS_API_SIGNUP_ALLOWED_EMAILS`. A delivery without the variable is refused before joining the tailnet. Migration `0001` is additive. Rollback is a promotion of the previous commit; its API ignores the new tables and variables.
