## Context

ADR-0011 chose Drizzle ORM with drizzle-kit, one migration history owned by `apps/api` (`drizzle.config.ts` collecting every context's schema, `migrations/` holding the history), each context's tables in its own PostgreSQL schema. No context exists yet. ADR-0006's hosting of PostgreSQL is constrained by the infrastructure repository: an application's relational data goes into the host's shared PostgreSQL instance (`postgres:18.6`, reached as `postgres:5432` on `platform_edge`) only if its loss is tolerable, and the operator's interim decision in `docs/backlog.md` `choose-durable-data-storage` treats everything Basis holds there as such until that entry is decided.

The infrastructure repository provisions an application's database by hand (`docs/onboard-an-application.md` §3.2): one role and one database named after the application (`basis-api`, the `deploy_apps` name on both hosts), and a generated password stored as a secret of the application's Environment under a name the application chooses; nobody holds a copy. The host's forced command extracts `docker-compose.yml` and `.env` into `/opt/basis-api` and runs `docker compose pull && docker compose up -d --wait`; it cannot run anything else.

`api-health` requires the API to start and answer `/health` with no external service reachable. `apps/api-e2e` starts the built API with the inherited environment. CI already runs `nx affected -t … integration …`; no project has the target.

## Goals / Non-Goals

**Goals:**

- The API holds a Drizzle connection to the database `DATABASE_URL` names, without its liveness depending on it.
- A migration history and a migration process in the image, run by every delivery before the API starts, failing the delivery when it fails.
- `DATABASE_URL` delivered to each host as a secret, built from the password the infrastructure recipe stores, printed nowhere.
- A Testcontainers setup any project's integration specs can use, and an `integration` target on `apps/api` that exercises the connection and the migration process.

**Non-Goals:**

- Any table, schema, repository, port or `TransactionManager` (ADR-0011 Rule 2); they arrive with the first context.
- Where the database token lives once a context's `infrastructure` library needs it: a library cannot import from `apps/api`. Recorded in `docs/backlog.md` as `share-the-database-connection`.
- The infrastructure repository's database probe before delivery (`docs/onboard-an-application.md` §4.5; the probe keys are already declared on both hosts). Recorded in `docs/backlog.md` as `probe-the-database-before-delivery`.
- Durable storage (`choose-durable-data-storage`), Redis and object storage.
- Running `apps/api-e2e` against a Testcontainers database; the e2e suite tests nothing that needs one yet.
- A local-development `docker compose` file for PostgreSQL.

## Decisions

1. **`pg` (node-postgres) with `drizzle-orm/node-postgres`, behind a global Nest module in `apps/api/src/database/`.** It provides a `pg.Pool` and the Drizzle database under injection tokens, sets `application_name` to `basis-api`, listens for the pool's `error` event (logging the error's class and code, never the URL) so an idle client's failure does not end the process, and ends the pool on application shutdown. ADR-0011 places Drizzle "only in `infrastructure/driven`" and the migration history in `apps/api`; the pool, the Drizzle instance and the migrator are the app's composition-root wiring, holding no repository, and where the tokens move once a context needs them is `share-the-database-connection`. A `pg.Pool` opens no connection until the first query, which is what keeps `/health` independent of the database. Alternative: `postgres` (postgres.js), equally supported by Drizzle; `pg` is the more widely deployed driver and its pool is explicit.
2. **`DATABASE_URL` is required, read once, and never echoed.** The module's factory refuses to create the pool when it is unset or empty, so a misconfigured process fails at start rather than falling back to libpq's `PG*` defaults and `localhost`. Errors name the variable, never its value. `apps/api-e2e`'s Vitest configuration sets `DATABASE_URL` to an address where nothing listens (`127.0.0.1:9`), which keeps its suite's "no external service" premise and its harness unchanged. `api-health`'s "depends on nothing outside the process" is read as a configured process with nothing reachable: an unset `DATABASE_URL` is a misconfiguration, not an absent service, and refusing it does not touch liveness.
3. **Migrations run in a one-shot Compose service, not in the API's startup.** `deploy/api/docker-compose.yml` gains `migrate`: the same image by digest, `command: [node, dist/migrate.js]`, `env_file: .env`, `restart: "no"`, `healthcheck: disable: true` (the image's `HEALTHCHECK` would otherwise apply to it), on `platform_edge`, confined like `api`. `api` gains `depends_on: migrate: condition: service_completed_successfully`. Verified locally with Compose v5.4.0: `up -d --wait` exits `0` once the one-shot has exited `0` and `api` is healthy, and exits `1` naming the service when it exits non-zero, leaving `api` created but not started. Alternatives: migrating inside the API's startup, which makes `/health` depend on the database (contradicting `api-health`); a migration step in the workflow, which cannot reach the database (only the host's forced command runs there); `drizzle-kit migrate` in the image, which ships a development tool and its dependencies to production.
4. **The migration process is `apps/api/src/migrate.ts`, built to `dist/migrate.js`.** It reads `DATABASE_URL` through the same function as the module, runs `drizzle-orm/node-postgres/migrator`'s `migrate` with the migrations folder resolved from its own location (`../migrations`), closes the pool and exits `0`; on any failure it prints a fixed sentence, the error's class, its PostgreSQL error code where it has one, and its message with every occurrence of the URL and of its password (raw and decoded) replaced by `[redacted]`, and exits `1`. A server's message is what makes a failed migration diagnosable, so it is redacted rather than withheld. Drizzle records applied migrations in `drizzle.__drizzle_migrations`. `apps/api/package.json` `files` gains `migrations`, so `pnpm deploy` puts the folder beside `dist` in the image.
5. **The history starts with a custom baseline migration** (`drizzle-kit generate --custom --name baseline`): a comment-only SQL file, its snapshot and the journal. Drizzle's migrator refuses a folder without a journal, and drizzle-kit writes none while no schema exists; a baseline gives the first delivery one recorded migration, which is what staging's confirmation observes. `drizzle.config.ts` points `schema` at `src/database/schema.ts`, which re-exports every context's schema and holds none yet; it sets `migrations.schema` to `drizzle` explicitly. A `db-generate` Nx target runs `drizzle-kit generate`.
6. **The secret is the password, and `DATABASE_URL` is rendered from it.** The infrastructure recipe generates the password and stores it as `BASIS_API_DATABASE_PASSWORD` in each Environment; storing a whole URL instead would make a rotation by that recipe leave the URL stale. `tools/delivery/src/render-env.ts` renders `DATABASE_URL="postgres://basis-api:<encodeURIComponent(password)>@postgres:5432/basis-api"` through the same escaping helper as every other line, and refuses an empty password. The role, database, host and port are literals, as the hostnames' parts already are: the recipe names both after the application, and the instance is `postgres:5432` on both hosts. The password reaches the action as an input `database-password`, the render step through `env:`, and the first step refuses without it; `.env` already has mode `0600` and is never printed. No TLS: the connection stays on the host's `platform_edge` bridge network.
7. **`check-compose` checks every declared service's resolved image**, so the migration that runs is the digest that was rendered, not a stale or tagged image. `promote.yml` runs `main`'s check against the promoted commit's Compose file, so a configuration without `migrate` passes: a commit from before this change remains promotable as a rollback, as `api-delivery` requires.
8. **Testcontainers helpers live in `@basis/shared-testing`** (`share-the-test-arrangement` design non-goal: "they arrive with the first database change"). `startPostgres()` starts `postgres:18.6` (the shared instance's image) through `@testcontainers/postgresql` and returns its URL and a stop function; `freshDatabase(url)` creates a uniquely named database and returns its URL. A Vitest `globalSetup` file under `apps/api/tests/integration/` starts one server per run and `provide`s its URL; specs `inject` it. The library depends on no workspace library, so the helpers are generic. Testcontainers tries each container-runtime strategy in turn (a dead `DOCKER_HOST` falls through to `/var/run/docker.sock`, verified in `testcontainers` 12.2.1's `getContainerRuntimeClient`) and throws `Could not find a working container runtime strategy` only when every one fails. So the guarantee is tested where it lives: the global setup takes the start function as a parameter defaulting to `startPostgres`, does not catch its failure, and its spec gives it one that throws. `testcontainers` brings dependencies with install scripts (`ssh2`, `cpu-features`, optional native acceleration); they are declined in `allowBuilds` (an explicit `false` where pnpm requires a decision), since the Docker socket needs neither.
9. **The `integration` target** is defined once in `nx.json` `targetDefaults` (`nx:run-commands`, `vitest run --config vitest.integration.config.mts` in `{projectRoot}`, depending on the project's own `build`, so the migration process's spec can run `dist/migrate.js`) and opted into by `apps/api` with an empty `integration` entry. The configuration is named so that `@nx/vitest` infers no target from it, as `apps/api-e2e`'s is. `apps/api/vitest.config.mts` excludes `tests/integration/**` and `**/*.integration.spec.ts`. The target is uncached: its result depends on Docker, which is no input.
10. **Documentation**: `AGENTS.md` _Deployment_ gains the migration service and the Environment secret, _Testing Strategy_ the shared Testcontainers helpers; `apps/api` gains a README stating how to generate a migration and run the migration process locally.

## Risks / Trade-offs

- [A failed migration leaves the API stopped on that host, since Compose recreates `api` before `migrate` fails] → the delivery fails visibly; the remedy is a fix through a new pull request, or on production a promotion of the previous commit. Data loss is tolerable under the interim decision.
- [Migrations are forward-only, so rolling production back by promotion runs older code against a newer schema] → Drizzle's migrator applies nothing older than the last applied migration, so the promotion succeeds; schema changes are to stay backward compatible for one release, a rule for the first change that adds tables.
- [Rollback by promotion runs `main`'s `check-compose` against the promoted commit's Compose file] → the check requires `migrate`'s digest only where `migrate` is declared, so a commit from before this change stays promotable; a rollback to it runs no migration and leaves the schema as it is.
- [The deploy refuses until the operator has provisioned `BASIS_API_DATABASE_PASSWORD` in each Environment] → stated in the proposal as a prerequisite; the refusal names the missing input.
- [`DATABASE_URL` sits in `/opt/basis-api/.env` on each host] → as every other runtime secret of applications on these hosts does; the file is written `0600` before delivery, and the deploy user owns it there.
- [The Testcontainers image tag duplicates the infrastructure repository's version] → a literal with a comment naming `platform/docker-compose.yml` there; a mismatch shows up as a behavioural difference, not a failure.
- [A run pulls `postgres:18.6` and Ryuk on first use] → the first CI run is slower; GitHub's runners have Docker.
