## Context

See proposal.md, Why. `apps/api` is a NestJS 12 application with a global `SessionGuard` (every route needs a session unless `@Public()`), a global `ProblemFilter` that answers an oversized body `413` as a problem document, and a global Standard Schema validation pipe (`api-http-errors`). Nest registers Express's JSON parser itself at `init()`, with its default limit of 100 kB, unless one named `jsonParser` is already applied. `identity` is the one context and the worked form of the layout (`libs/identity/{application,infrastructure,contracts}`, CQRS buses, tables in the context's schema, a composition root outside `driving/` and `driven/`, `add-identity-authentication` decision 5). The root `eslint.config.mjs` already lists `metrics` among the contexts. Each host's database holds only data whose loss is tolerable (`choose-durable-data-storage`).

HC Webhook (`mcnaveen/health-connect-webhook`, AGPL-3.0, v1.9.25 on 2026-10-20) reads Health Connect on the phone and `POST`s JSON to configured URLs, on an interval of at least 15 minutes, at fixed times, or on demand, with custom headers per URL and no signature. The body is one object: `timestamp` (when the payload was built), `app_version`, `timezone`, an optional `deleted` array, and one array per data type with at least one record, keyed in snake_case (`steps`, `sleep`, `heart_rate`, `resting_heart_rate`, `exercise`, …). Raw records carry `metadata` with `id`, `data_origin` (the writing app's package), `recording_method` (`actively_recorded`, `automatically_recorded`, `manual_entry`, `unknown`), an optional `device` (`manufacturer`, `model`, `type`) and `last_modified_time`. A record's time is `time`, or `start_time` and `end_time`; a sleep session has `session_end_time` and `stages` (each with a `stage` name); an exercise session has `type`, a string (Health Connect's exercise type in string form), `start_time` and `end_time`; a `deleted` entry is `{ type, id }`, `type` being the payload key of the deleted record's data type. Heart rate and four other series arrive as raw samples or as N-minute aggregates (with `avg`, `min`, `max`), per a setting in the app. A default sync reads a rolling 48 hours, sends only what is new since the previous successful sync per type, and resends edited and late records with the same `metadata.id`. Any `2xx` is success; a failure is retried at the next sync. (Read from the repository's `docs/webhook.md` while drafting.)

Drizzle 0.45.4 wraps a failed query in `DrizzleQueryError`, whose message is `Failed query: <sql>` followed by `params: <params>` (read from `drizzle-orm/errors.js` while revising), and `ProblemFilter` logs a defect's name, message and stack (`api-http-errors`), not its `cause`.

## Goals / Non-Goals

**Goals:**

- The reference device's data reaches the server, owned by the signed-in user, unchanged, so nothing about it is lost before it is understood.
- What arrived can be read without access to the host: which types, written by which app and device, recorded how, with which sleep stages and exercise types, and how late.

**Non-Goals:**

- The findings, ADR-0001's confirmation or adjustment, and the answers to open questions 1 and 2: `record-phase-0-findings` (operator's decision).
- Normalising into `MetricRecord`, idempotency, deduplication of resent records, `MetricRecorded`, source status: Phase 1's ingestion, which retires this intake (`retire-the-health-connect-intake`).
- A credential other than a session (`issue-ingestion-keys`), our own Expo client, background-sync behaviour on the phone (verified by hand, Testing Strategy).
- Deleting or exporting stored deliveries.

## Decisions

1. **The bridge authenticates with a session token** (operator's decision). The operator signs in through `POST /auth/google` and configures HC Webhook with the custom header `Authorization: Bearer <token>`. The intake routes are ordinary routes behind the global `SessionGuard`; the caller comes from `CurrentUser`. A session lasts 30 days, longer than Phase 0 needs; when it expires or is revoked the bridge's log shows `401`, and the operator signs in again. Alternatives: a per-user ingestion key (a mechanism ADR-0001's own client does not need; recorded as `issue-ingestion-keys`); a shared deployment secret (the data would belong to no user, against Conventions, Ownership).

2. **A delivery is stored as received.** `POST /health-connect/deliveries` takes a body that is a JSON object with a string `timestamp` and a string `app_version`, keeping every other key (Zod `looseObject`); anything else is `400` (`api-http-errors`). The handler stores the whole parsed object as `jsonb`, with the caller's identifier and the time the delivery arrived, and answers `204`. It does not interpret, deduplicate or merge records: Phase 0 must see what the bridge sends, resends included. Answering any `2xx` is what HC Webhook needs to advance its watermark.

3. **The intake route accepts 10 MB; the rest keep 100 kB.** A first sync carries up to 48 hours of every enabled type; at one-minute heart-rate resolution with metadata that is around a megabyte, beyond Nest's default. `apps/api/src/http/body-parsers.ts` exports `useBodyParsers(app)`, called by `main.ts` before `listen`, which applies `express.json({ limit: '10mb' })` to `POST` requests whose path is exactly `/health-connect/deliveries`, with or without a trailing slash (a small middleware checks the method and the path before delegating, since Express matches `app.use` paths by prefix, while its routing ignores a trailing slash, so both forms reach the controller) and then `express.json({ limit: '100kb' })` to every path. Express's parser skips a body already parsed, so the intake's parser governs its route; and because a parser named `jsonParser` is then applied, Nest does not add its own. A body over a route's limit is `413` as before. `express` becomes a direct dependency of `apps/api`, at the version `@nestjs/platform-express` resolves. The parser runs before `SessionGuard`, so an unauthenticated caller can still make the API parse up to 10 MB on this one route (Risks). Alternatives: raising the limit for every route (opens every route, the public `POST /auth/google` included, to large bodies); `app.useBodyParser` (global only).

4. **The summary is computed from the stored deliveries.** `GET /health-connect/deliveries/summary` answers `HealthConnectSummary` for the caller's deliveries, all of them (a few thousand in a month at the 15-minute minimum, mostly small; risk below):
   - `deliveries`: `count`, `firstReceivedAt`, `lastReceivedAt` (null when none), and the distinct `appVersions` and `timezones` seen.
   - `types`: for each data-type key that held an array (every top-level key except `timestamp`, `app_version`, `timezone` and `deleted`), `records` (the number of elements across deliveries), `firstRecordAt` and `lastRecordAt` (over each record's time, decision 5), and counts by `origins` (`metadata.data_origin`), `recordingMethods` (`metadata.recording_method`) and `devices` (`"<manufacturer> <model> (<type>)"`, omitting absent parts, or `unknown` when no `device`). A record without `metadata` counts as `unknown` in all three. For a type whose records may be samples or aggregates, `shapes` counts `sample` and `aggregate` (an element with `avg`, or with `avg_delta_celsius`, is an aggregate); for other types `shapes` is absent.
   - `sleep`: `sessions` and counts of `stages` by their `stage` value; absent when no `sleep` array arrived.
   - `exercise`: `sessions` and, per exercise `type`, its `count` and counts by `recordingMethods`, which answers open question 2; absent when no `exercise` array arrived.
   - `delays`: per type, `toHealthConnect` (a record's `metadata.last_modified_time` minus its time) and `toApi` (the delivery's arrival minus `metadata.last_modified_time`), each as `{ count, medianSeconds, p90Seconds, maxSeconds }` over records with both values, rounded to whole seconds; a type with no such record has neither.
   - `deleted`: counts of `deleted` entries by `type`.

   Values the summary reads are taken only when they have the expected JSON type; anything else counts as `unknown` or is skipped, so a malformed record never fails the summary. The computation is a pure function in `application`, unit-tested over fixtures shaped like HC Webhook's documented payload.

5. **A record's time** is its `end_time`, else `session_end_time`, else `time`, parsed as an ISO 8601 instant with an offset; `firstRecordAt` uses `start_time` when present. Both forms of HC Webhook's timestamp setting (UTC or local with offset) parse to the same instant. The median and 90th percentile use the nearest-rank method over the delays in seconds, each delay rounded to the nearest whole second. A negative delay (a record modified before its time ends, or a phone clock ahead of the server's) is kept, since it is itself a finding.

6. **Library layout follows `identity`'s** (`add-identity-authentication` decision 5), with no `domain`:
   - `libs/metrics/contracts` (`@basis/metrics-contracts`, `scope:metrics`, `type:contracts`): the Zod schemas `HealthConnectDeliveryRequest` (decision 2) and `HealthConnectSummaryResponse` (decision 4).
   - `libs/metrics/application` (`@basis/metrics-application`, `type:application`): command `RecordHealthConnectDelivery` and query `SummarizeHealthConnectDeliveries`, each in its own folder with its handler; write port `HealthConnectDeliveryRepository` (add) and read port `HealthConnectDeliveryReader` (the caller's deliveries, each as its arrival time and payload); the pure `summarizeHealthConnectDeliveries`; `METRICS_HANDLERS`.
   - `libs/metrics/infrastructure` (`@basis/metrics-infrastructure`, `type:infrastructure`): `driven/` holds the Drizzle table (`pgSchema('metrics')`) and the two adapters; `driving/` holds `HealthConnectDeliveriesController`; the composition root `src/metrics.module.ts`, `MetricsModule`, outside both.

   Reading HC Webhook's format in `application` departs from the context map, which puts the Health Connect anti-corruption layer on the driving side: it is acceptable only because the intake stores no metric and is retired by Phase 1, whose ingestion translates in the driving adapter and hands `application` source-agnostic records (Conventions, Metrics).

   All three are built and are `dependencies` of `apps/api`. `MetricsModule` needs no options. Each library's README states that the intake is temporary.

7. **The table.** `metrics.health_connect_deliveries`: `id` (UUID, generated by the database), `user_id` (UUID, not null), `received_at` (`timestamptz`, not null, the database's `now()` at insert) and `payload` (`jsonb`, not null), with an index on `(user_id, received_at)`. `user_id` carries no foreign key to `identity.users`: a context's tables reference another context's identifiers without reaching into its schema, as every later user-owned table will. Migration `0002`, generated by drizzle-kit from the table re-exported through `apps/api/src/database/schema.ts`, is additive, so the previous release runs against it. `api-persistence`'s scenario "Identity's tables are in its schema", which lists every table outside the migration record, gains `metrics.health_connect_deliveries`; it keeps its recorded name, since `openspec validate --strict` refuses a `MODIFIED` requirement that drops a scenario by name (`add-identity-authentication` decision 9).

8. **Nothing of a delivery is logged.** No handler or adapter logs a delivery's body or a value from it. A `400` problem's `errors` carry paths and messages, not values (`api-http-errors`). A failed insert would otherwise reach the log through `DrizzleQueryError`'s message, which holds the query's parameters, the payload among them; so the repository adapter catches any error from its insert and throws instead `HealthConnectDeliveryNotStored`, an `Error` with the fixed message `The Health Connect delivery could not be stored.` and no `cause`, which `ProblemFilter` answers `500` and logs by name, message and stack, none holding a value of the delivery. The reader adapter's query takes only the user's identifier and needs no such guard. The same exposure in `identity`'s session insert (a digest in the parameters, against `identity-authentication`'s requirement that no digest is logged) is not this change's: `keep-query-parameters-out-of-defect-logs` in `docs/backlog.md`.

9. **Verification.** Unit specs: the summary function over fixtures (types, origins, methods, devices, shapes, sleep stages, exercise types, delays, deleted, malformed values), the handlers with in-memory fakes, and the controller through an application built with `MetricsModule` and fakes (`401` without a session, `400` for a body that is not a delivery, `204`, the summary). Integration specs in `apps/api/tests/integration/` cover the adapters against a migrated database (a stored delivery reads back unchanged with its arrival time; one user's summary excludes another's deliveries; an insert that fails, such as one into a database whose `metrics` table was dropped, throws `HealthConnectDeliveryNotStored` and the logs hold no value of the delivery). End-to-end: the built app answers `401` for both routes without a session, and a body over 100 kB but under 10 MB reaches the intake route's guard rather than being refused `413`, while the same body to another route is `413`.

## Risks / Trade-offs

- [A session token in the bridge's settings on the phone] → it grants the operator's whole API access for up to 30 days; sign-out revokes it. Phase 0 runs on the operator's own phone.
- [Health data on a loss-tolerable database] → acceptable for validation; losing it costs re-collection. Durable storage is `choose-durable-data-storage`, due before the calibration period.
- [HC Webhook sends every type the user enables, including sensitive ones (reproductive health, blood glucose)] → the README tells the operator to enable only the types the habits need: steps, distance, active and total calories, heart rate, resting heart rate, heart rate variability, sleep, exercise.
- [A delivery over 10 MB, likeliest on a first sync with raw heart-rate samples] → it is refused `413`, nothing is logged on our side, and the bridge retries with the same window until the records fall out of its 48 hours. The README tells the operator to watch the bridge's log and the summary's `lastReceivedAt`, and, on `413`, to enable fewer types for the first sync; a higher limit would be a follow-up.
- [Heart rate as N-minute aggregates hides per-record detail] → the README tells the operator to set heart rate to raw samples (Full resolution), which zones need; aggregates are still counted under `shapes`.
- [Unauthenticated callers can make the API parse up to 10 MB at the intake route before the guard refuses them] → bounded to one route and one method, temporary, and capped at 10 MB; the public host already accepts 100 kB on every route.
- [The summary reads every delivery of the caller per request] → bounded by Phase 0's few weeks; Phase 1 retires the route.
- [Resent records count twice] → intended: the summary reports what arrived, and `metadata.id` lets the findings tell resends apart; deduplication is Phase 1's.
- [HC Webhook is a third party's app] → it receives no credential but the operator's session token and sends only to the URL configured; AGPL-3.0 governs its distribution, not our use.

## Migration Plan

Migration `0002` is additive. After merging, once staging is healthy, the operator installs HC Webhook, grants it Health Connect read access for the types above, adds a webhook with staging's URL and a staging session token, and runs a manual sync; confirmation reads the summary (tasks). After promotion the operator points the bridge at production with a production session token and leaves interval sync on. Rollback is a promotion of the previous commit; its API ignores the `metrics` schema, and the bridge's requests get `404` until the intake returns.
