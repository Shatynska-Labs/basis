## Context

See proposal.md, Why. `apps/api/src/database/database.module.ts` declares `DATABASE_POOL` and `DATABASE` as symbols and types the database as `NodePgDatabase<typeof schema>`, where `schema.ts` re-exports every context's tables for the connection and for drizzle-kit (ADR-0011). `eslint.config.mjs` holds ADR-0012 §7's tag table: `type:infrastructure` may depend on `type:application`, `type:domain`, `type:contracts`, `type:core` and `type:util`, and a context scope may depend on `scope:shared`. Every workspace library's `package.json` points at `src/index.ts`, and so far only specs and `tests/` of `apps/api` import one (`@basis/shared-testing`). The API is built by `@nx/js:swc` into `apps/api/dist`, which compiles only the app, and the image is `pnpm deploy --filter api --prod` of the built package. In this layout a runtime import of a workspace library resolves to TypeScript sources under `node_modules`, which Node does not run.

## Goals / Non-Goals

**Goals:**

- A context's `infrastructure` library takes the API's database from a library it is allowed to import, under the same token the API provides it on.
- The built API, and the image built from it, run with that library.

**Non-Goals:**

- Moving the pool, `DATABASE_URL` handling, `APPLICATION_NAME` or the migration process out of `apps/api`. They configure the one process that owns the connection, and no library needs them.
- Implementing `TransactionManager` (decision 6 records only its location).
- Giving the other shared libraries a build. They gain one when production code first imports them at runtime.
- Adding a context, a table or a repository.

## Decisions

1. **Library: `libs/shared/infrastructure`, `@basis/shared-infrastructure`, tags `scope:shared` and `type:infrastructure`** (operator's decision). It is ADR-0012's shared kernel extended by its infrastructure layer, tagged the way the layer is tagged everywhere else. Alternatives: a `shared/persistence` library under a new tag (one more tag and lint rule for one library), or moving the whole database module into the library (it would carry `DATABASE_URL` handling and the migration process's dependency with it, for no consumer).
2. **Sources split into `src/driving/` and `src/driven/`** (operator's decision, as ADR-0012 §1 has it for a context's `infrastructure`). The database token is something adapters call, so it goes in `src/driven/database.ts`. `src/driving/` is not created until something goes in it. `src/index.ts` is the only file outside the two folders and only re-exports. A spec in the library checks the layout (see the spec).
3. **What moves: `DATABASE` and the `Database` type, nothing else.** `DATABASE` stays a `Symbol`. A symbol is unique per module instance, and the API and every context reach the one built copy of the library through the workspace's single package, so they share it. `apps/api`'s module imports the token and re-exports none: its spec and its integration tests take `DATABASE` from `@basis/shared-infrastructure`. `DATABASE_POOL` stays private to `apps/api`.
4. **`Database` is `NodePgDatabase` with no schema type parameter, and the connection is created without `{ schema }`.** A shared library cannot import the schemas `apps/api` collects, so it cannot name `typeof schema`. The schema only types Drizzle's relational query API (`db.query.<table>`), which ADR-0011 already excludes ("no relation navigation through objects"). Repositories use the query builder over the tables their own context defines. `schema.ts` stays as drizzle-kit's input, and its comment changes to say so. Alternative: a generic `Database<TSchema>` that a context narrows. Each context would see only its own tables in the type while the runtime object held every context's, and nothing would use it.
5. **The library is buildable and ships compiled.** Its `package.json` points `exports`, `main` and `types` at `dist/`, `files` lists `dist`, and `tsconfig.lib.json` emits JavaScript (`emitDeclarationOnly: false`). The `@nx/js/typescript` plugin then infers a `build` target. `apps/api` declares it as a `dependency` (`workspace:*`), and the API's `build` target `dependsOn: ["^build"]`, so `nx build api`, the image's build, builds it first. `test` already depends on `^build`, and so do `integration` and `e2e` (both through `build`), so Vitest resolves the built library. `typecheck` runs `tsc --build` over project references (`pnpm nx sync` adds the library to `apps/api/tsconfig.app.json`), which builds the library's declarations first, and the inferred `typecheck` target also depends on `build`. `lint` uses no type-aware rules, so it needs no declarations. `pnpm deploy --prod` copies the package with its `dist`. A prototype confirmed this: the deployed directory's `node dist/main.js` started and mapped `/health`. Alternatives: bundling the API with esbuild or webpack (it changes the delivery's build for one symbol), or a `development` export condition pointing at sources (a second resolution path to keep in step, for no current need).
6. **`TransactionManager`, recorded only.** The AsyncLocalStorage adapter goes in `libs/shared/infrastructure/src/driven/` beside the database it opens transactions on. The port is declared in each context's `application`, as ADR-0011 rule 2 puts it there, and the shared adapter satisfies it structurally, bound to the context's port token in the context's infrastructure module. A shared `application` library would also work, but no such tag exists, and adding one is a larger amendment than this change needs. The library's README records this.
7. **Boundary rule: `type:infrastructure` may depend on `type:infrastructure`.** The scope rows already stop a context from reaching another context's non-`contracts` libraries, so together they allow exactly a context's infrastructure → the shared infrastructure. ADR-0012 §7's `type:infrastructure` row gains "`type:infrastructure` of `scope:shared`", and §6's table gains the library with tag `type:infrastructure`. The library has no `bannedExternalImports`, like every infrastructure library. Its `scope:shared` row already confines it to the shared kernel. This amends the tables, as `share-the-test-arrangement` did, and needs no superseding ADR.
8. **Verification.** A boundary spec in the library lints sample sources through ESLint's Node API, as `libs/shared/testing/src/boundaries.spec.ts` does. `apps/api`'s `database.module.spec.ts` resolves the database through the shared token. The `api-e2e` suite already starts the built API, so it shows the build and resolution path, and a spec in `apps/api-e2e` starts the `pnpm deploy` output the same way, so the deploy path is checked in CI and not only by a local `docker build`.

## Risks / Trade-offs

- [A stale `dist/` lets a test pass against old code, or a clean checkout fails where a local one passes] → every target that resolves the library depends on `^build` or builds it through project references (decision 5), and task 3.2 runs the verification after deleting the library's `dist/`. Nx caches `build` by its inputs, so a change to the sources rebuilds it.
- [The boundary spec lints a virtual file in a context `type:infrastructure` library, and none exists] → the spec reads the computed constraint table for that case, as the shared-testing boundary spec does, and lints a real file wherever a project exists (`apps/api`, `libs/shared/core`).
- [Dropping `{ schema }` from the connection removes `db.query`] → nothing uses it, and ADR-0011 excludes relation navigation.
- [The library and `apps/api` resolve different peer variants of `drizzle-orm`, so `Database` is not assignable from what `apps/api` creates] → the library declares `drizzle-orm` and `pg` at the exact versions `apps/api` declares, `@types/pg` comes from the workspace root for both, and task 1.1 checks that the lockfile holds one `drizzle-orm` variant.
- [Two copies of the library at runtime would split the symbol] → pnpm links one workspace package. `pnpm deploy` copies one.

## Migration Plan

The API's behaviour and its database are unchanged, so no migration is needed. The image gains `node_modules/@basis/shared-infrastructure`. Rollback is a promotion of the previous commit.
