Derived by `change-test-writer` from the approved delta specs at commit `e287f8e`, before implementation. Not an artifact the OpenSpec schema knows: `openspec instructions apply` does not surface it, so it has to be read on purpose.

This pass only added test files. No existing test was edited, deleted or disabled, and no implementation was written: no module, function, type or stub. Two temporary probe copies were written and deleted within the pass (see _State of the new tests at authoring_); neither remains.

## How to run a named test

Tests are named `file › describe › test`. Run one from its project directory with Vitest's name filter. Put `~/.nvm/versions/node/v24.9.0/bin` first on `PATH`.

- unit, `apps/api` (`test` target): `cd apps/api && npx vitest run src/health-connect-intake.spec.ts -t "<test name>"`
- unit, the new libraries (`test` target, once task 1.1 creates the projects with their `vitest.config.mts`): `cd libs/metrics/application && npx vitest run src/summarize-health-connect-deliveries.spec.ts -t "<test name>"`; `cd libs/metrics/contracts && npx vitest run src/health-connect-delivery-request.spec.ts -t "<test name>"`
- integration: `pnpm nx run api:build`, then `cd apps/api && npx vitest run -c vitest.integration.config.mts tests/integration/<file> -t "<test name>"` (needs Docker)
- end-to-end: `pnpm nx run api:build`, then `cd apps/api-e2e && npx vitest run -c vitest.e2e.config.mts src/health-connect-intake.spec.ts -t "<test name>"`

## Unresolved project questions

1. **Where the new names are exported.** Assumption: `HealthConnectDeliveryRequest` (a Zod schema, used with `.safeParse`) is exported from `libs/metrics/contracts/src/index.ts`, and `summarizeHealthConnectDeliveries` from `libs/metrics/application/src/index.ts`; both specs import `./index.js`. Depends: `req` (all), `sum` (all).
2. **The summary function's shapes.** Assumptions: the input is the read port's answer as `{ receivedAt: Date; payload: unknown }[]`; every "counts by" in the output is a record from value to count (`{ "com.sec.android.app.shealth": 3 }`); the exercise types sit under `exercise.types[<type>] = { count, recordingMethods }` (decision 4 does not name the key); an absent `sleep`, `exercise`, `shapes` or delay entry is `undefined`/missing, not `null`. Instants are compared as instants, so a `Date` or an ISO string both pass. Depends: `sum` (all); the over-HTTP summary tests in `int` assume the same JSON shapes.
3. **`useBodyParsers`.** Assumption: `apps/api/src/http/body-parsers.ts` exports `useBodyParsers(app)`, taking the `INestApplication` that `NestFactory.create` or `Test…createNestApplication` returns, applied after creation and before `listen`, with no `bodyParser: false` option needed (design decision 3: Nest skips its own once a parser named `jsonParser` is applied). Depends: `unit-api` (all), `int` (all).
4. **`GoogleIdTokenVerifier` as the override token.** Taken from the existing `identity-authentication.integration.spec.ts`, where it works. Depends: `int` (all), to sign callers in.
5. **What "MB" is.** Assumption: 2²⁰ bytes, as Express reads `10mb`. The 2 MB bodies (2 MiB) are under 10 MB on either reading, and 11 MiB is over it on either reading. Depends: the size tests in `unit-api`, `int` and `e2e`.
6. **No stack skill.** The library has no skill for TypeScript, NestJS or Vitest; the tests were written on the `testing` floor and the project's conventions alone.
7. **"The time of the request".** Assumption: the stored `received_at` (the database's `now()`) within 5 seconds of the interval during which this process sent the request, since the database clock is the container's. Depends: `int › … › a delivery is stored with its caller`.
8. **The new libraries' specs are not collected until task 1.1** creates the projects with a `test` target and `vitest.config.mts`, as `identity`'s have. Until then `pnpm nx run-many -t test` does not run them, and a green run says nothing about them.
